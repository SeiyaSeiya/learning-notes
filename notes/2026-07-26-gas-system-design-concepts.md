# GASによるシステム開発で重要な設計概念（疎結合・べき等性・実行時間対策など）

- 学んだきっかけ: GASプロジェクト群の保守性・機能追加のしやすさを上げたいと思い、Claudeと「疎結合とは何か」「GAS開発で他に重要な設計概念は何か」を整理した。エンジニアとしての勉強目的でまとめておく。

## 1. 疎結合とは何か

モジュール（関数・ファイル・システム）同士の依存関係を最小限にし、互いの内部実装を知らなくても連携できる設計。対義語は密結合で、あるモジュールの変更が芋づる式に他へ波及する状態。疎結合であれば、インターフェース（関数のシグネチャや入出力の形）さえ変わらなければ、中身を差し替えても影響が閉じ込められる。

GASでは同一プロジェクト内の全`.js`ファイルが実行時に1つのグローバルスコープへ結合され、ESモジュールのような明示的な境界がない。放置すると関数名衝突や「どこからどこが呼ばれているか分からない」状態＝密結合になりやすく、他言語以上に意識的な設計が必要になる。

## 2. 疎結合を実現する具体的な手法

- **I/Oとロジックの分離**: `SpreadsheetApp`や`UrlFetchApp`などGAS組み込みオブジェクトに依存するコードと、入力を受け取って値を返すだけの純粋なロジックを分ける。ロジック部分はNode環境でテストしやすくなり、シート構造の変更がロジックに波及しなくなる。
- **レイヤー分離**: トリガー/エントリポイント層（薄い呼び出し口）→ ビジネスロジック層（純粋関数）→ データアクセス層（シート・外部API呼び出しをラップ）の3層に分ける。上位層は下位層の実装詳細を知らず、入出力の契約だけに依存する。
- **外部API呼び出しをファサード関数で包む**: `UrlFetchApp`を直接あちこちで呼ばず、`fetchXxxApi(params)`のような専用関数に集約する。API仕様変更時の修正箇所を1箇所に絞れる。
- **namespaceパターンでグローバル衝突を防ぐ**: ESモジュールがない代わりに、オブジェクトで擬似的なモジュール境界を作る。

  ```js
  const VocExtract = {
    fetchComments(sheetId) { /* ... */ },
    classify(comment) { /* ... */ },
  };
  ```

- **設定・秘匿情報をコードから切り離す**: `PropertiesService`で管理すると、設定変更のためにコードを触らなくてよくなる（セキュリティ目的だけでなく疎結合の効果もある）。
- **JSDocで型・契約を明示する**: TypeScriptがない分、引数・戻り値の型と役割をJSDocで書いておくと、関数間の暗黙の契約が可視化される。
- **プロジェクト間の共通処理はApps Scriptライブラリ機能を検討**: `gas-feedback-generate`と`gas-voc-extract`のように独立プロジェクトが増える場合、コピペで重複させるとロジックの同期が取れなくなる。ライブラリ化すれば1箇所の修正で済むが、バージョン管理の手間とのトレードオフなので、重複が3箇所目に増えたあたりで検討するくらいが現実的。

## 3. べき等性（同じ処理を何度実行しても結果が変わらない設計）

GASはトリガーの再実行や`UrlFetchApp`のタイムアウト後の再送などで、同じ処理が意図せず2回走ることがある。「行を追記する」処理をべき等でない形で書くと、再実行のたびに重複データが増える。処理の先頭で「すでに処理済みか」をチェックする、一意なIDで上書き更新にする、といった設計にしておくと事故が減る。

## 4. 実行時間制限への対処（分割実行・再開可能な設計）

6分（トリガー実行は30分）の壁があるため、大量データを扱う処理は「どこまで処理したか」を`PropertiesService`に保存し、時間ベーストリガーで続きから再開できる形にするのが定石。これは単なる制約対応というより「処理の状態を外部（コード変数ではない場所）に持たせる」という設計思想そのもので、分散システム設計にも通じる考え方。

## 5. 排他制御とべき等性の組み合わせ

`LockService`で同時実行を防ぐのは定石だが、ロックだけに頼ると単一障害点になりやすい。多少の重複実行が起きても壊れない設計（べき等性）を土台にし、ロックはあくまで最適化として使う、という位置づけが安全。

## 6. クォータとキャッシュ

`UrlFetchApp`やスプレッドシート操作には日次クォータがある。`CacheService`で外部API呼び出し結果を一時保存する、スプレッドシートの読み書きを`getValues()`/`setValues()`でまとめる、といった対応はパフォーマンスだけでなくクォータ枯渇を防ぐ設計判断でもある。

## 7. テスト容易性

GASは統合テストがしにくい環境（`SpreadsheetApp`などの組み込みオブジェクトに依存するため）。だからこそ純粋関数として書けた部分を意図的に増やし、`clasp push`前にNode.js上でJestなどを使ってローカルテストできるようにする設計判断に価値がある。「疎結合」と「テスト容易性」は同じ設計判断（I/Oとロジックの分離）から得られる別の果実、と捉えるとつながりが分かりやすい。

## 8. 可観測性（ログ設計）

`console.log`を闇雲に撒くのではなく、「どの処理のどの段階か」「どの入力データに対する処理か」が後から追えるよう構造化して出す。エラー発生時に管理者へメール通知する仕組みを組み込んでおくと、Stackdriverログを毎回見に行かなくてもよくなる。

## 9. 最小権限の原則

`appsscript.json`の`oauthScopes`を必要最小限にするのは、一般的なセキュリティ原則（Principle of Least Privilege）のGASでの現れ。スコープを絞ることで、スクリプトが侵害されたときの被害範囲を限定できる。

## 10. バージョン管理とデプロイ戦略

`clasp push`は即座に本番へ反映されるため、変更前に`clasp deploy`でバージョンを切っておく、テスト用の別デプロイを用意しておくなど「ロールバックできる状態を常に確保する」考え方もGAS特有の運用上重要。

## まとめ

- 疎結合・べき等性・実行時間対策・クォータ管理・可観測性・最小権限・デプロイ戦略は、根っこでは「変更に強く、壊れたときに復旧しやすいシステムをどう作るか」という一つの軸でつながっている。
- GASにおける最重要の実践は「I/O（GAS組み込みオブジェクト依存）とロジック（純粋関数）を分離すること」。これ一つで疎結合・テスト容易性・保守性の多くが同時に改善する。
- 既存コードへの適用は、CLAUDE.mdの方針通り「大きな書き換えより小さく安全な変更」から。触る関数から少しずつレイヤー分離していくのが現実的。
