# 外部SaaSの仕様変更で自動処理が「静かに」壊れた話（Google Meetの保存先移行とDrive走査の移行対応）

- 学んだきっかけ: `gas-voc-extract`（MTG文字起こしからGeminiでVOC抽出→Slack自動投稿するGASプロジェクト）で、「条件を満たしているはずなのに一部のMTGだけ文字起こしが取得できていない」という不具合が発生。原因調査から恒久対応の実装までをClaude Codeと進めた。**原因は自分のコードのバグではなくGoogle Workspace側の仕様変更**で、調査プロセス・外部依存の設計・GASコードのローカル検証手法まで学びが多かったので整理する。

## 1. 「一部だけ失敗する」バグの調査は、まず"静かにスキップされる経路"を全部列挙する

症状は「その日のMTGのうち、いくつかだけシートに出力されていない」。全滅ならすぐ気づくが、**一部だけ落ちると数日間誰も気づかない**のが厄介だった。

この手のバグでまずやるべきは、**処理対象を落としうる分岐をコードから漏れなく列挙すること**。今回の対象関数はループ内で `continue` する経路が3つしかなかった。

1. ファイルの作成日が対象日と一致しない
2. ファイル名から取れたコードが、対象コードのホワイトリスト配列に無い
3. ファイル名がどちらの正規表現にもマッチしない

そして**3つとも、ログも出さずエラーにもならず静かにスキップする**実装だった。列挙した上で1つずつ現物のデータで潰していけば、消去法で原因に近づける。

- 教訓: `continue` / 早期 `return` / `indexOf() === -1` のような箇所は「静かな失敗」の温床。調査時はここを地図にする。実装時はログを1行足しておくだけで後の調査が劇的に楽になる。

## 2. 仮説は「コードが参照している情報の上限」から否定できる

自分の初期仮説は「カレンダーの出欠で"不参加(❌)"の人がいるのが原因では？」だった。これは**コードを見た瞬間に否定できる**類の仮説だった。

- 対象コードは `CalendarApp` も Calendar API も使っておらず、`appsscript.json` の有効な高度サービスも Drive と Docs だけ。
- つまり**このコードが判定材料にできる情報はDrive上のファイル名・作成日・置かれたフォルダの3つだけ**で、出欠情報は物理的に参照されていない。

「そのコードがアクセスできる情報の範囲」を先に確定させると、無関係な仮説を安いコストで捨てられる。マニフェスト（有効サービス・OAuthスコープ）は、その上限を知るための一次情報として便利。

## 3. 正規表現は実データを流して検証する（GASを動かす必要はない）

「ファイル名がマッチしていないのでは」という仮説の検証は、正規表現をNodeにコピーして想定ファイル名を流すだけで済んだ。

```js
const RE = /^(.+)_([a-zA-Z0-9-]+)\s-\s.+(Transcript|メモ)$/;
[ "会議タイトル_<コード> - 2026/07/24 10:00 JST～Transcript",   // ✅
  "会議タイトル_<コード> - メモ",                                // ❌ 日時部分が無いと落ちる
  "会議タイトル_<コード> - 2026/07/24 …Transcript (1)",          // ❌ 末尾の重複サフィックス
].forEach(n => console.log(RE.test(n), n));
```

こうやって**「通るケース」と「落ちるケース」を並べて出す**と、確認すべき現物（実際のファイル名）が具体化する。「たぶん大丈夫」で済ませず、境界を明示するのが大事。

### 副産物として見つけた既存バグ: 分岐の順序でフォールバックが死ぬ

コードは「コード自体に `_` を含むパターン」を先に試し、次に「単一コードのパターン」を試す2段構えだったが、前者にマッチしたら**ホワイトリストに無くてもその場で `continue`** していた。

```js
// 修正前（悪い）: 合成コードが一覧に無いと、単一コードの判定に到達できない
const m2 = name.match(/^(.+)_([a-zA-Z0-9-]+)_([a-zA-Z0-9-]+)\s-\s.+$/);
if (m2) {
  if (!LIST.includes(m2[2] + "_" + m2[3])) continue;  // ← ここで打ち切られる
  ...
}
const m1 = name.match(/^(.+)_([a-zA-Z0-9-]+)\s-\s.+$/);  // ← 到達しない
```

結果、`会議タイトル_MTG_<コード>` のようにコードの手前に英数字トークンが入るタイトルが静かに落ちていた。**「マッチしたか」と「採用できるか」を混同すると、後段のフォールバックが機能しなくなる**。判定に失敗したら次の候補へ進む（`continue` せず素通りさせる）のが正しい。

## 4. 真因: 外部SaaSがファイルの保存先を変えていた

調べていくと、対象日以降のファイルがそもそも走査対象のフォルダに存在しなくなっていた。原因はGoogle Workspace側の仕様変更だった。

- Google Meetの会議メモ・文字起こし・録画の保存先が、マイドライブの `Meet Recordings` から **`Google Meet/<会議ごとのサブフォルダ>`** へ変更された。
- 旧 `Meet Recordings` は `Google Meet` の中へ移動され、`Legacy Meet Recordings` へ改名される。
- 繰り返し会議は全インスタンスが1つのサブフォルダにまとまる。
- **参加者側のドライブには実体ではなくショートカットが置かれる。**
- 公式アナウンス自身が「**フォルダ名やIDに依存するAPIスクリプト・自動化ワークフローを監査せよ**」と明記していた。まさに該当した。

### Rapid Release と Scheduled Release（＝症状が"一部だけ"になった理由）

Google Workspaceの新機能には2つの配信トラックがあり、管理コンソールでドメイン単位／OU単位に設定できる（既定は Rapid）。

| トラック | 挙動 |
|---|---|
| Rapid Release（早期リリース） | 機能公開と同時に配信 |
| Scheduled Release（定期リリース） | Rapidから1〜2週間遅れて配信。管理者が事前準備できるようにするため |

さらに重要なのが、**どちらのトラックでもドメイン内で1〜3日かけてユーザー単位に段階展開される**こと。つまり:

- 同じ組織内でもメンバーごとに切替日がバラバラになる
- 移行期間中は新旧のフォルダ構成が混在する
- 結果として「**その日のMTGのうち一部だけ落ちる**」という、原因が読みにくい症状になる

**「全滅ではなく一部だけ壊れる」のは、外部プラットフォームの段階展開を疑う強いシグナル**という教訓を得た。

## 5. 「自分のアカウントで再現しない」は仕様変更が無い証拠にならない

切り分けの途中で「自分でテスト会議を開いたら従来のフォルダに保存された」という観察があり、一瞬仮説が揺らいだ。しかしこれは矛盾ではなかった。

- 段階展開なので**自分のアカウントがまだ未適用なだけ**。
- そもそも成果物は**主催者のドライブ**に保存されるので、自分が主催したテストでは自分のアカウントしか検証していない。落ちていたMTGの主催者は別の人だった。
- つまり**検証対象のアカウントが違っていた**。再現テストは「誰のアカウントで、誰が主催した会議を見ているか」まで揃えないと意味がない。

### ファイルのACLとフォルダのACLは別物

もう1つ有用だった観察: 該当ドキュメントは開けるのに、Googleドキュメントの `ファイル > 詳細` の「場所」が `-` と表示された。

- これは**親フォルダへのアクセス権が無い**ことを意味する。つまり「ファイルは共有されているが、それが入っているフォルダは共有されていない」状態。
- 移行前（旧フォルダ配下）のファイルでは「場所」が表示され、移行後のファイルでは `-` になる。**前後比較すると、保存先が変わったことの直接証拠になる**。
- Driveのフォルダ走査を前提にした自動化は「ファイルが見えること」ではなく「**フォルダが見えること**」に依存している、という当たり前だが見落としやすい点。

## 6. コード側の対応: フォルダ名依存を"配列"にして新旧併走させる

恒久対応で入れた変更と、その理由。外部仕様変更に追随する際の型として使えそうなので残す。

- **走査対象フォルダ名を配列化**して新旧すべてを対象にする（`Google Meet` / `Meet Recordings` / `Legacy Meet Recordings`）。移行期間中は混在するので、どちらか一方に切り替えるのではなく**併走させる**のが正解。
- **`getFiles()` は直下のファイルしか返さない**。会議ごとのサブフォルダに入る新構成では、`getFolders()` による再帰が無いと0件になる。フォルダ名を直すだけでは不十分だった。
- **同一実体へ複数経路で到達する**ようになった（`Legacy Meet Recordings` は「`Google Meet` の子フォルダ」かつ「名前一致でもヒット」する／ショートカット経由でも同じファイルに届く）。フォルダIDとファイルIDの集合で重複排除しないと、コピー処理が二重に走ってゴミが増える。
- **ショートカットは実体に解決してから扱う**。`getMimeType()` が `application/vnd.google-apps.shortcut` で、`getTargetId()` / `getTargetMimeType()` で実体を辿れる。ショートカットに対してコピーを実行しても**ショートカットのコピーができるだけ**でURLも実体を指さない。
- **所有者の取り方を変えた**。従来は「フォルダの所有者」を担当者としていたが、ショートカット経由だとフォルダ所有者が参加者になり担当者を誤る。**ファイルの所有者を優先**し、取れない場合のみフォルダ所有者にフォールバックした（旧構成では両者が一致するので挙動不変）。

### コードで直せないものは切り分けて明言する

新しいフォルダはGoogleが新規作成したものなので、**旧フォルダの共有設定を引き継がない**。つまりコードを直しても、各メンバーがフォルダを共有し直すまで収集は再開しない。

- 「コードの修正」と「運用作業」を混ぜて報告すると、片方だけ終わって"直ったつもり"になる。**コード側では解決できない部分は明示的に切り出して伝える**。
- 併せて権限レベルの確認も価値がある。今回はコピー処理なので**元ファイルの閲覧権限で足り、編集権限が必要なのはコピー先だけ**。依頼のハードルを下げられるので、「本当にその権限が必要か」は一度確認した方がよい。

## 7. 「無言の失敗」を仕組みで潰す

そもそも数日間気づかれなかったのは、コード側に検知の仕組みが無かったからだった。ここは仕様変更とは独立した設計の反省点。

- 対象フォルダが見つからないと `console.log` して `return` するだけ。**そのファイルには try/catch もエラー通知も1つも無かった**（他のファイルには入っていた）。→ try/catch とSlack通知を追加。
- **0件だったときも通知する**。ただし土日は会議が無いのが正常なのでノイズになる。ここで既存の平日判定関数を流用しようとしたが、その関数は「**今日**」を見る実装で、月曜の実行（対象は日曜）で誤通知になる。**対象日の曜日で判定する関数を別に用意した**。日付処理は「今日」と「対象日」の混同が典型的なオフバイワンの罠。
- **最後に一括書き込みする設計は、途中の例外や実行時間上限で全件失う**。GASは6分（トリガーは30分）の上限があるので、経過時間の安全弁を入れて、上限に近づいたら走査を打ち切り**途中までの結果を書き込んでから**通知するようにした。「全部失う」より「部分成功＋アラート」の方が運用しやすい。
- **リカバリ関数を作るなら冪等性が必須**。対象日を指定して再実行できる手動関数を追加したが、重複行のスキップを入れないと同じVOCがSlackへ二重投稿される。既存キー（日付＋コード＋タイトル）でスキップするようにした。
- **グローバル定数の暗黙の前提にも注意**。出力先シート名が「前日基準の `yyyy/MM`」というグローバル定数だったため、月をまたぐリカバリ実行で別月のシートに書き込む事故になり得た。対象日から導出するよう変更。

## 8. GASのコードをローカルで検証する方法（Node の `vm` ＋ GASグローバルのスタブ）

GASは `SpreadsheetApp` などの組み込みオブジェクトに依存するためローカルでの単体テストが難しい、とよく言われる。ただ**「GASのランタイムで動かせない」だけで、ソースは素のJavaScript**である点を利用すれば、ロジックはローカル検証できる。

前提として、GASは `import`/`export` を使わず**全ファイルが実行時に1つのグローバルスコープへ結合される**。つまり各ファイルは「外部のグローバル変数を参照するだけのスクリプトテキスト」なので、そのグローバルを自分で用意すればNodeで評価できる。

```js
const vm = require('vm'), fs = require('fs');

// GAS組み込み + config定数の偽物を用意する
const ctx = {
  console,
  CLIENT_CODE_ARRAY: ['code-a', 'code-b'],
  notifyErrorToSlack: (e) => console.log(`[Slack] ${e.message}`),
  Utilities: { formatDate: (d, tz, fmt) => /* 必要な書式だけ実装 */ },
  DriveApp: {
    getFoldersByName: (name) => /* hasNext()/next() を持つ偽イテレータ */,
    getFolderById: (id) => /* 権限が無いケースは throw させる */,
  },
  SpreadsheetApp: { getActiveSpreadsheet: () => /* 偽シート */ },
};
vm.createContext(ctx);

// 本物のソースを"無改変で"評価し、同じコンテキスト内で関数を呼ぶ
vm.runInContext(fs.readFileSync('Meet.js', 'utf8'), ctx);
vm.runInContext('主対象の関数()', ctx);
```

偽のDrive木構造に「新構成」「旧構成」「ネストした改名済みフォルダ」「ファイルのショートカット」「フォルダのショートカット」「権限が無くて解決に失敗するショートカット」「対象外の日付のファイル」を混ぜておくと、再帰の到達範囲・重複排除・日付フィルタ・所有者のフォールバックを一度に確認できた。同じ処理を2回走らせて重複行が増えないこと（冪等性）も確認できる。

### この手法の限界を混同しないこと

これで検証できるのは**自分が書いた制御フローの正しさだけ**。

- **スタブは「自分が想定したAPI挙動」であって本物ではない。** 想定を間違えていれば、テストは通るのに実機で動かない。
- 実際の権限・クォータ・実行時間、外部の命名規則、`getFoldersByName` が本当に共有フォルダを返すか等は検証できない。
- したがって**「ロジックのバグは潰した」までで、動作確認は未完了**と正しく言うべき。ここを「テスト済みです」と報告すると事故る。ログで何を確認すれば実機検証が完了するかまでセットで用意しておくと良い。

## 9. 作りかけの暫定対応を捨てた判断

途中で「Driveのフォルダ走査を諦めて、カレンダー予定の添付ファイルから文字起こしのURLを取る」暫定対応を実装した。が、**実行アカウントがゲストに入っていないMTGの成果物にはアクセスできない**ことが分かり、業務要件を満たさないので破棄した。

- 反省: **「技術的に取得できる」と「業務要件を満たす」は別**。着手前に「1件だけ手で開いてアクセスできるか確かめる」をやっていれば、実装せずに判断できた。前提の実測を最優先にすべきだった。
- Gitの扱いとして学んだこと: **未マージのブランチ上のコミットは `main` に影響しない**ので、不要になっても慌てて `git reset --hard` する必要はない。「マージしない」だけで十分で、履歴に残しておけば後から参照・復元もできる。破棄の手段として reset を選ぶのは、失うものがあるときだけ。
- ただし**同じブランチに後続の作業を積む場合は注意**。不要なコミットが残ったブランチをマージすると不要な変更も一緒に入るので、後続コミットで明示的に削除して「マージ後の最終状態」を正しくしてから統合した。マージ前に `git diff main --stat` で**純粋な差分**を確認するのが確実。

## 10. まとめ

- 「一部だけ失敗する」バグは、**静かにスキップされる経路を全列挙**して1つずつ潰す。`continue` / 早期 `return` / `indexOf() === -1` が地図になる。
- **仮説はコードが参照できる情報の上限（マニフェスト・使用API）から安く否定できる**。
- **全滅ではなく一部だけ壊れたら、外部プラットフォームの段階展開を疑う**。SaaSのリリースには配信トラック（Rapid / Scheduled）とユーザー単位の段階展開があり、同一組織内でも挙動が混在する。
- 外部SaaSの**フォルダ名・IDに依存する自動化は壊れる前提**で作る。名前を配列にして新旧併走、階層は再帰前提、ショートカット・重複到達を考慮する。
- **コードで直せない部分（共有設定などの運用作業）は切り出して明言する**。混ぜると"直ったつもり"になる。
- **無言の失敗を仕組みで潰す**。エラー通知、0件通知（ただし判定は「今日」ではなく「対象日」で）、部分成功の保存、冪等なリカバリ関数。
- GASのロジックは **Node の `vm` ＋ 組み込みオブジェクトのスタブ**でローカル検証できる。ただし検証できるのは制御フローだけで、実機確認は別物と正しく区別する。
- 実装前に**前提を1件だけ実測する**。技術的可能性と業務要件は別。
