# 実運用ログからの切り分けと、"安全弁"の閾値を実測で決めるということ（Driveのショートカット権限・外部リソースはIDで解決される）

- 学んだきっかけ: [2026-07-27: 外部SaaSの仕様変更で自動処理が「静かに」壊れた話](2026-07-27-google-meet-drive-folder-migration-and-silent-failure.md) の続き。恒久対応を実機（GAS）で動かして実行ログを読んだ結果わかったこと、および**自分が「安全のため」に入れた仕組みが実運用では有害だったので削除した**話を整理する。前回はコードを書くまで、今回は動かしてからの学び。

## 1. エラーログの山の中から「成功している行」を探すと、仮説を安く棄却できる

初回実行のログは「解決に失敗しました」が何行も並び、一見すると全体が動いていないように見えた。実際こちらも「サブフォルダが複数あるせいで走査に失敗しているのでは」と疑った。

しかし**成功している1行**が決定的な反証になった。

```
18:22:03  フォルダ名: Google Meet, 所有者: ○○, フォルダid: 1NLU…
18:22:05  コピー対象を発見: <会議タイトル>_<コード> - 2026/07/24 09:59 JST - Gemini によるメモ
```

このファイルは親フォルダの直下ではなく**サブフォルダの中**にある。つまりこの1行が出ている＝**サブフォルダの再帰は機能している**という証明になる。「失敗が目立つ」と「機能していない」は別で、**成功例が1つでもあれば構造的な故障は否定できる**。

- 教訓: エラーログを読むときは、まず**成功しているログを探す**。どこまでは動いているかの境界を引くと、疑うべき範囲が一気に狭まる。
- 併せて、失敗しているケースと成功しているケースの**差分**（今回は「誰が主催した会議か」）に注目すると原因に直結する。

### 「確認しました」の対象がズレていないか

このとき自分は「該当ファイルはスクリプトのアカウントでも開けることを確認した」と報告したが、**開いて確認したのは成功している方のファイル**だった。失敗しているファイルでは確認していなかった。

- **検証は「失敗している対象そのもの」で行わないと意味がない。** 似て見える別のもので確認して「問題ない」と結論すると、切り分けが振り出しに戻る。
- 報告するときも「何を対象に確認したのか」を明示すると、こういうズレが早く見つかる。

### 実行をキャンセルすると結果が1件も残らない設計だった

途中でキャンセルした実行では、シートに1行も書かれていなかった。走査結果を**最後にまとめて一括書き込みする**設計のため、書き込み前に止まると全部消える。

- GAS では `setValues()` の呼び出し回数を減らすため一括書き込みが定石だが、その副作用として「途中で止まると全損」になる。**途中経過を残したいかどうかは意識して選ぶ**べきポイント。

## 2. 「フォルダが見える」と「ファイルが読める」は別（ショートカットが挟まると依頼先が変わる）

失敗ログの正体はこれだった。

```
ショートカットの解決に失敗しました: <ファイル名>
(No item with the given ID could be found. Possibly because you have not edited
 this item or you do not have permission to access it.)
```

Drive のこの定型文は「IDが存在しない」より「**そのIDのアイテムにアクセス権がない**」という意味で出ることがほとんど。今回は「ショートカットが指している実体のファイルに権限がない」状態だった。

構造はこうなっていた。

- **主催者**のドライブの会議ごとのサブフォルダ → **実体のファイル**
- **参加者**のドライブにも会議ごとのサブフォルダが作られる → 中身は**ショートカットだけ**

つまり参加者のフォルダを共有してもらっても、得られるのはショートカットだけで**実体は読めない**。ここが重要な運用上の含意になる。

- 旧構成では、そのフォルダには実体しか入っていなかったので「**フォルダを共有してもらう＝ファイルが読める**」が成立していた。この前提が仕様変更で崩れた。
- **共有を依頼すべき相手は「参加者」ではなく「その会議の主催者」**。逆に言えば、失敗ログの一覧がそのまま「誰に依頼すればよいか」のリストになる。
- 一般化すると、**ファイルのACLと、それが入っているフォルダのACLは独立**。フォルダ走査を前提にした自動化は「ファイルが見えること」ではなく「**フォルダ（と中の実体）が見えること**」に依存している。

## 3. 「対策」が新しい障害を作った: 安全弁の閾値は実測値で決める

前回の実装で、こういう"安全弁"を入れていた。

```js
/** 走査を打ち切る経過時間。実行上限に達して全件失う事故を防ぐための安全弁 */
const SCAN_TIME_LIMIT_MS = 4.5 * 60 * 1000;
```

意図は「6分の実行上限に達して例外で落ちると、一括書き込み前なので全件失う。だから手前で打ち切って部分結果を保存し、通知する」。**考え方としては筋が通っているが、閾値が現実と合っていなかった。**

- GAS の実行時間上限は**トリガー実行だと最大30分**あり、しかも**実際の過去のトリガー履歴では6分を超えて正常完了していた**。
- 結果、4.5分で走査が打ち切られ、**取りこぼしが発生した上に「時間切れで打ち切りました」という誤アラートまで飛ぶ**という、対策が障害を生む状態になった。
- 指摘を受けて削除した。

### ここから得た教訓

- **保険や安全弁は「勘」でなく「実測値」で閾値を決める。** 今回は「過去のトリガー実行履歴」という一次情報が手元にあったのに参照していなかった。所要時間の実績を見れば4.5分が短すぎることはすぐ分かった。
- **中途半端な打ち切りは「静かな取りこぼし」を生む。** フェイルセーフのつもりで入れた仕組みが、誤検知装置として働くと信頼性を下げる（アラートが狼少年になると、本当の異常も無視されるようになる）。
- **「まだ起きていない障害」への対策より、実際に起きている問題を優先する。** 6分超過は起きていなかったが、取りこぼしと誤通知は実際に起きた。予防的な仕組みは、それ自体が不具合の原因になりうる。
- **削除するときは「なぜ入れないのか」を書き残す。** `CLAUDE.md` に「経過時間による打ち切りは意図的に入れていない（トリガーは30分あり実測でも6分超で完走していたため）」と明記した。理由なく消すと、将来また誰かが同じ善意で再導入する。**「やらない理由」も設計情報**として記録する価値がある。

## 4. 外部SaaSが管理するリソースは、名前だけ真似て先回りしても機能しない

移行がまだ来ていないメンバーについて「**先に手動で同名のフォルダを作っておけば良いのでは**」というアイデアが出た。これは有効ではない。

- 外部サービス（今回は Meet）は保存先を**名前で探しているのではなく、自分が作ったフォルダのID**を内部的に参照して書き込む。手動で作った同名フォルダは**別IDの無関係なリソース**なので、そこに保存されることはない。
- そもそも移行が適用されるかは「そのユーザーの段階展開の状態」で決まり、フォルダの有無とは無関係。
- おまけに Drive は**同名フォルダを許容する**ため、後から本物が作られると同名フォルダが2つ並ぶ。名前で走査する自動化から見ると「フォルダはあるのに0件」という**診断を誤らせる状態**が生まれる。切り分け中に自らノイズを増やすことになる。

一般化すると、**名前は人間向けのラベルで、システム間の参照はIDで解決されている**。だから:

- 相手（外部サービス）が作るリソースを、こちら側で名前だけ模倣して先回りしても連携しない。
- 逆に**こちら側のコードが「名前で探す」実装だったから壊れた**。依存の方向を意識すると、どちらを直すべきかがはっきりする（今回はこちらを「複数の名前を許容する」形に直した）。

## 5. 移行では「新規作成されたもの」と「同一実体のまま移動したもの」を区別する

権限がどこで切れるかは、この区別で予測できる。今回の移行を分解するとこうなっていた。

| 対象 | 移行の内容 | 共有設定 |
|---|---|---|
| 新しい親フォルダ・会議ごとのサブフォルダ | **新規作成** | 引き継がれない → **共有し直しが必要** |
| 旧フォルダ | 新フォルダの中へ**移動＋改名**（実体は同じ） | **維持される** → 過去分へのアクセスは失われない |

- **新規作成されたリソースには権限が付いてこない**が、**移動・改名されただけのリソースは実体が同じなので権限が残る**。「フォルダ名が変わった＝別物になった」ではない。
- そして**親フォルダを一度共有すれば、以降その中に作られる子にも権限が継承される**。つまり依頼は会議ごとではなく**1回で済む**。この性質を確認しておくと、運用依頼の設計（何回・誰に・どの粒度で頼むか）が変わる。
- 未移行のユーザーは旧構成のまま動くので、**新旧併走の実装にしておけば「待てばよい」状態**になる。段階展開される変更に対しては、切り替えではなく併走が正解だった。

## 6. まとめ

- **エラーログは、まず成功している行を探す。** どこまで動いているかの境界を引けば疑う範囲が狭まり、成功例が1つあれば構造的な故障は否定できる。
- **検証は「失敗している対象そのもの」で行う。** 似た別のもので確認して「問題ない」と結論すると切り分けが振り出しに戻る。
- **ファイルのACLとフォルダのACLは独立。** ショートカットが挟まると「フォルダは見えるが実体は読めない」が起きるので、権限の依頼先が変わる。
- **安全弁の閾値は実測値で決める。** 実績データ（実行履歴）という一次情報を見ずに入れた保険は、取りこぼしと誤アラートという新しい障害を作る。予防的な仕組み自体が不具合になりうる。
- **「やらない理由」も設計情報として残す。** 消した対策の理由を書かないと、将来同じ善意で再導入される。
- **外部サービスが作るリソースを名前だけ真似ても連携しない。** システム間の参照はIDで、名前は人間向けのラベル。
- **移行では「新規作成」と「移動・改名」を区別する。** 権限が切れるのは前者だけ。親フォルダの共有は子へ継承されるので依頼は1回で足りる。
