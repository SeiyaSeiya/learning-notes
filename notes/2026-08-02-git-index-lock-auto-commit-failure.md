# learning-notesの自動commitが数日間失敗し続けた原因（`.git/index.lock`の幽霊ロック）

- 学んだきっかけ: 7/31、[launchdによる自動commit・push](2026-07-14-launchd-auto-commit.md)が動いていないことに気づき、Cowork（Claude Desktop）に原因調査を依頼したセッション。

## 概要
7/30の06:30を最後に、`learning-notes-auto-commit.sh`（launchd経由・手動実行とも）が原因不明のまま失敗し続けた。手動実行してもエラーメッセージが一切ターミナルに表示されないため、当初はスクリプト内にハードコードされた`claude`コマンドのパス（`/opt/homebrew/bin/claude`）が怪しいと仮説を立てたが、これは誤りだった。実際の原因は、gitの排他制御用ロックファイル（`.git/index.lock` / `.git/HEAD.lock`）が異常終了によって残ってしまい、それ以降のすべての`git commit`を機械的にブロックし続けていたこと。

## 症状
- `bash scripts/learning-notes-auto-commit.sh`を手動実行しても、ターミナルには何も表示されずコマンドが失敗（終了コード非0）で戻ってくる。
- launchd経由でも同様に失敗。

## なぜターミナルに何も表示されなかったか
スクリプトは`.env`ファイルが見つからない場合を除き、エラーはすべて自前の`log()`関数で`~/.claude/cron-logs/learning-notes-auto-commit.log`にしか書き込まない設計になっている。そのため手動実行しても標準出力・標準エラーには何も出ず、「無言で失敗した」ように見えていた。原因調査はまずこのログファイルの中身を確認するところから始まる。

## 調査の経緯
1. **最初の仮説（誤り）**: `CLAUDE_BIN="/opt/homebrew/bin/claude"`のパスがハードコードされており、Homebrew版とネイティブインストーラ版でインストール先が異なる（[2026-07-11のメモ](2026-07-11-claude-desktop-vs-cli.md)参照）ため、環境によっては存在しないパスを指してしまう可能性がある、と推測した。
2. `which claude`で実際のパスを確認したところ`/opt/homebrew/bin/claude`で一致しており、この仮説は外れだった。
3. 実際にログファイル（`~/.claude/cron-logs/learning-notes-auto-commit.log`）を確認したところ、以下が判明した。

   ```
   2026-07-31 06:30:59 claude exit code: 0
   2026-07-31 06:30:59 claude output (truncated): `.git/index.lock` の削除は保護されたファイルへの操作として
   ブロックされました。状況をご報告します。現在、別のClaudeプロセス（cronの自動コミットジョブ、
   PID 72658, 6:30AM開始）が同じリポジトリで動作中で、`.git/index.lock`が残っています。
   このロックファイルのタイムスタンプは前日(7/30 13:48)で...
   2026-07-31 06:30:59 FAILURE: no new commit was created (HEAD unchanged: c6a437...)
   ```

   `claude`自体は正常終了（exit code 0）しているが、`git commit`が実行されず`HEAD`が変わっていないため、スクリプトが`FAILURE`として検知していた。

## 根本原因: gitのロックファイルと「幽霊ロック」
- gitは`index`（ステージング領域）や`HEAD`を書き換える際、直接上書きするのではなく、まず`.git/index.lock`・`.git/HEAD.lock`という一時ファイルを作成し、そこに書き込んでから本体にリネームするという手順を踏む。複数のgitプロセスが同時に同じファイルを壊さないようにするための排他制御。
- 正常に処理が終われば、このロックファイルはgit自身が最後に削除する。一瞬だけ存在して消える、本来は目に見えないファイル。
- 今回はロックファイルのタイムスタンプが7/30 13:48。同日に[「過去のcommitを修正する方法（amend/rebase -i/cherry-pick）」の検証作業](2026-07-30-git-commit-history-rewrite-amend-rebase-cherrypick.md)を行っていたため、その途中でgitプロセスが異常終了（ターミナルを閉じる・強制終了・スリープ等）し、後片付け（ロック削除）が実行されないまま残ってしまったと考えられる。
- gitには「もう動いていないプロセスが残したロック」なのか「本当に動いているプロセスのロック」なのかを区別する手段がない。そのため、実体のない「幽霊ロック」が残っている限り、以後のすべての`git commit`が「他のプロセスが処理中」と誤認されて拒否され続ける。

## なぜClaude（headless）が自分で直せなかったか
これはバグではなく、スクリプトの設計上意図した制約だった。`learning-notes-auto-commit.sh`は`claude -p`呼び出し時、`--allowedTools`で`git add` / `git commit` / `git status` / `git diff` / `git log`のみを許可しており、`rm`のような任意のファイル操作は許可していない（[launchdメモ](2026-07-14-launchd-auto-commit.md)にある「pushはLLMにやらせない」という設計方針と同じ考え方で、コミット操作以外の権限を与えないようにしていた）。
そのためClaudeはロックファイルの存在に気づき、削除していいか確認しようとしたものの、そもそも実行権限がなくブロックされ、結果として「確認させてください」というテキストだけを返して何もせず終了していた。ヘッドレス実行には応答できる人間がいないため、これが7/31から8/2まで繰り返され続けていた。

## 対処
1. Coworkのサンドボックス経由でリポジトリの`.git/index.lock`・`.git/HEAD.lock`を確認し、両方とも7/30 13:4x台の古いタイムスタンプで、実体のあるgitプロセスは存在しないことを確認。
2. 2ファイルを削除。
3. `bash scripts/learning-notes-auto-commit.sh`を再実行し、commit・pushが正常に成功することを確認。

## 再発防止: スクリプトへの自動解消ロジック追加
同じ状況で毎回人手を介さずに復旧できるよう、`learning-notes-auto-commit.sh`に「幽霊ロックの自動解消」処理を追加した（`REPO_DIR`へ`cd`した直後、ブランチチェックの前に実行）。

- `.git/index.lock` / `.git/HEAD.lock`が存在し、**かつ**タイムスタンプが10分以上前で、**かつ**`pgrep -f "git.*$REPO_DIR"`で該当リポジトリを参照する稼働中のgitプロセスが見つからない場合のみ、「幽霊ロック」とみなして自動削除する。
- 10分未満の新しいロックや、実際にgitプロセスが動いている場合は一切手を出さず、ログに記録するだけにとどめる（安全側に倒す設計）。

## 学び
- 自動化スクリプトでエラーをログファイルにしか書かない設計は、「手動実行でも同じ結果になる」という一貫性は保てるが、原因調査の初手が「まずログを見る」になる前提を運用側が忘れないようにする必要がある。
- LLMに危険な操作をさせないための権限制限（`--allowedTools`を絞る設計）は、意図しない副作用として「本来LLMが直せたはずの些細なトラブル（幽霊ロックの削除など）まで自分で直せなくする」ことがある。安全性と自己修復力はトレードオフになりうる。
- gitのロックファイルは「排他制御のための一時ファイルであり、異常終了時には手動または明示的なロジックで後片付けが必要になりうる」という前提を持っておくと、同種のトラブル（`rebase`や`amend`の途中終了など）に遭遇したときに切り分けが速くなる。
