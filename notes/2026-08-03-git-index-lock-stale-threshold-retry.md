# `.git/index.lock`の自動解消閾値をすり抜けて手動実行が失敗した件

- 学んだきっかけ: [launchdによる自動commit・push](2026-07-14-launchd-auto-commit.md)の`learning-notes-auto-commit.sh`を手動実行したら失敗し、Cowork（Claude Desktop）に原因調査を依頼したセッション。過去に対処した[「幽霊ロック」問題](2026-08-02-git-index-lock-auto-commit-failure.md)と症状は同じだが、原因は少し異なっていた。

## 概要
`bash scripts/learning-notes-auto-commit.sh`を手動実行したところ失敗した。原因は`.git/index.lock`の残存で、スクリプトには既にこれを自動解消する仕組み（10分以上前・かつ実行中のgitプロセスが無い場合のみ削除）が入っていたが、実行した時点ではロックの経過時間がまだ10分未満だったため、自動解消の対象にならなかった。少し待ってから再実行すると、自動解消ロジックが働いて正常に完了した。

## 症状
- `git status`では変更（README.mdとlaunchdメモの編集）が未コミットのまま残っていた。
- `git add`を試すと`fatal: Unable to create '.../index.lock': File exists.`で失敗する状態だった。
- `.git/index.lock`が空ファイルとして残存していた。

## 調査の経緯
1. Coworkのサンドボックス上でリポジトリの状態を確認し、`.git/index.lock`の存在とタイムスタンプを確認。
2. `git add -A`を試して同じ`File exists`エラーを再現し、ロックが実際にgit操作をブロックしていることを確認。
3. スクリプトには既に「10分以上前・かつ稼働中のgitプロセスが無い場合のみロックを自動削除する」ロジック（[2026-08-02のメモ](2026-08-02-git-index-lock-auto-commit-failure.md)で追加済み）が入っている。今回確認した時点でのロックの経過時間は10分未満だったため、まだ自動削除の対象になっていなかった。
4. ロックの経過時間が10分を超えるのを待ってから`bash scripts/learning-notes-auto-commit.sh`を再実行したところ、自動解消ロジックが働いてロックが削除され、`git add` / `git commit` / `git push`まで正常に完了した。

## 調査時の余談: Cowork経由での再現には別の失敗要因が混ざる
Claudeに調査を依頼した際、Cowork側のサンドボックス（Linux環境）で同じスクリプトをそのまま実行すると、`/opt/homebrew/bin/claude`や`$REAL_HOME`ベースのログディレクトリなど、macOS固有の絶対パスが存在しないために別の理由で即座に失敗した。これはスクリプトがmacOS本体での実行（Terminalまたはlaunchd経由）を前提にしているためで、今回の本質的な原因（ロックの残存）とは無関係。原因調査を依頼する際は、どちらの環境で再現した失敗かを区別しておくと絞り込みが早くなる。

## 学び
- 「N分以上前なら削除する」という閾値ベースの自動解消は、ロックが作られてから閾値を超えるまでの間に実行が重なると素通りしてしまう。閾値は「稼働中のロックを誤って消してしまわないための安全マージン」であって、「常に自動で直る」ことまでは保証しない。
- この種の失敗はロックが閾値を超えるまで待って再実行するだけで直ることが多い。まず`~/.claude/cron-logs/learning-notes-auto-commit.log`のログと`.git/index.lock`の有無・タイムスタンプを確認し、再実行で直るかを試すのが最短の切り分け方法。
