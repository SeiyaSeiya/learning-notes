# claspの`clasp push`が「Project settings not found」で失敗する原因と、1リポジトリに複数push先を持つ構成について

- 学んだきっかけ: とあるGASプロジェクトで`clasp push`を実行したところ「Project settings not found」というエラーが出た。以前は問題なくpushできていたはずなのに失敗する、という状況をClaude Codeと一緒に調査した。

## 原因: `.clasp.json`はカレントディレクトリ直下しか見ない

`clasp push`は、実行した**カレントディレクトリ直下**の`.clasp.json`を見て、どのGASプロジェクト（Script ID）へpushするかを判断する。今回のリポジトリは、1つのGitリポジトリの中に

```
プロジェクトルート/
├── container/
│   └── .clasp.json   ← コンテナ側のScript ID
└── library/
    └── .clasp.json   ← ライブラリ側のScript ID
```

という構成で、リポジトリのルート直下には`.clasp.json`が存在しない。ルートディレクトリで`clasp push`を実行していたため、`.clasp.json`が見つからずエラーになっていた。`container/`または`library/`へ`cd`してから実行したところ問題なくpushできた。

**教訓**: `clasp push`が失敗したら、まず`pwd`と`cat .clasp.json`（あるいは単に`ls .clasp.json`）で「今どのディレクトリにいて、どのScript IDに向けてpushしようとしているか」を確認する癖をつけるとよい。

## 副次的に気づいたこと: Script IDが似た名前の別プロジェクトと混同しやすい

調査の過程で、教えてもらったGASエディタのURLのScript IDが、実は同名っぽい別リポジトリ（検証用に先行して作っていたプロトタイプ版）の`library/.clasp.json`に紐づくものだったと判明した。プロジェクト名が似ている（本番版とプロトタイプ版）と、どちらのリポジトリ・どちらのサブディレクトリのScript IDか取り違えやすい。`grep -rl "<scriptId>" ~/Projects/gas-project`のように、Script IDそのものでリポジトリ横断検索すると、どのディレクトリが対象か機械的に特定できて確実。

## 一般論: 1つのGitリポジトリに複数のGAS（clasp）プロジェクトを持つのは一般的か

これは`gas-project/.claude/CLAUDE.md`のようなマルチプロジェクト管理の文脈に限らず一般論として成り立つ。clasp自体が「1ディレクトリ＝1つの`.clasp.json`＝1つのScript ID」という前提のツールなので、関連する複数のGASプロジェクト（例: コンテナバインドスクリプトと、それが呼び出す共通ライブラリ）を、サブディレクトリに分けて1つのGitリポジトリにまとめて管理するのはよくある構成。ライブラリと利用側スクリプトのようにライフサイクルが密接に絡む場合、バージョン管理をリポジトリ単位でまとめられるメリットがある。

トレードオフは今回まさに踏んだ点で、「今どのサブディレクトリにいるか」を常に意識しないと、意図しないプロジェクトへpushしてしまう（あるいはルートディレクトリで実行して今回のように失敗する）リスクがあること。対策は、pushの前に確認する習慣をつけるか、`SETUP.md`のようなドキュメントに「どのサブディレクトリがどのScript IDに対応するか」の対応表を明記しておくこと。
