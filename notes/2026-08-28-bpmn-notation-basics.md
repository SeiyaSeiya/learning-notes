# BPMNとは何か：業務フロー表記法の基礎と実務での使い方

- 学んだきっかけ: 業務内で初めて耳にした「BPMN」について、顧客と開発側の認識ズレをなくすために必要らしいと聞き、詳しく調べた。ちょうどCREからカスタマーサクセス（CS）へ新しい業務効率化システムを紹介する資料に使えそうだったので、実際にdraw.ioで描くことを前提に調査した。

## 1. BPMNとは何か

- Business Process Model and Notation（ビジネスプロセスモデル表記法）の略。OMGという標準化団体が策定している。
- 業務の流れ（プロセス）を、誰が見ても同じ解釈になるよう、記号の意味があらかじめ決まった図で描くための表記法。
- 目的は「業務側（顧客）」と「開発側（エンジニア）」の間で、業務フローの認識をすり合わせること。文章や口頭説明だけだと、伝わるたびに少しずつ解釈がズレていく問題を防ぐのが狙い。

## 2. なぜ必要か："すれ違い"の名作 ブランコの絵

- ソフトウェア開発で有名な風刺画「How projects really work（プロジェクトの実話）」が象徴的。「顧客が説明した要件」→「PMの理解」→「アナリストの設計」→「プログラマのコード」→「営業の表現・約束」と工程を経るごとに、誰も悪意なく手も抜いていないのに、成果物が少しずつ本来の要求からズレていく、というもの。
- 原因は、業務フローを「言葉」だけで伝えていること。文章には書いた人の前提や省略が多く、読む人によって解釈の余地が生まれる。
- BPMNは、言葉ではなく共通ルールを持った「図」で業務の流れを固定することで、このズレを早期に発見できるようにする。「絵に描いて確認する」というワンステップが入るだけで、大きな認識ズレは起きにくくなる。

## 3. 基本の4つの記号

覚えるべき記号はまず4つで十分。

| 記号 | 見た目 | 意味 |
|---|---|---|
| 開始イベント | 細い線の丸 | プロセスの起点 |
| タスク | 角丸の四角 | 一つの作業 |
| ゲートウェイ | ひし形 | 条件分岐・合流 |
| 終了イベント | 太い線の丸 | プロセスの終点 |

- さらに「レーン（スイムレーン）」という横（または縦）の帯で、「誰が（何が）その作業をするか」を区切って描くのが一般的。担当者・部門ごと、あるいは「人の作業」と「システムの自動処理」で分けると、業務側が一番知りたい境界線がそのまま図になる。

## 4. 実務での想定用途：CREからCSへの新システム紹介

- CREが新しく作った業務効率化システムをCS部に紹介する場面は、まさに「ブランコの絵」の伝言ゲームが起きやすいシチュエーション。CRE側は仕組みを深く理解しているが、CS側は業務観点で「この場合は誰が何をするのか」を知りたい。
- BPMNの考え方を使い、「CS担当がやること」と「システムが自動でやること」をレーンで分けて描くと、自動化の境界線と例外時の対応者が一目でわかる資料になる。
- ただし紹介資料に使うときは、フルスペックのBPMN記法にこだわりすぎない方がよい。CS側がBPMN記法に馴染みがないと、記号の意味を読み解くコスト自体が新しい認識ズレを生みかねない。記号は「開始・終了・タスク・ゲートウェイ」の4つに絞り、レーンは「人」と「システム」の2段階で十分。

### 具体例：問い合わせ対応フロー（新システム導入後）

```mermaid
flowchart LR
    subgraph CS担当
        A((問い合わせ受信)) --> B[内容を確認する]
        B --> C{よくある質問か?}
        C -- 該当しない --> D[CS担当が個別対応する]
        D --> E((完了・個別))
    end
    subgraph システム（自動）
        F[自動回答を送信する] --> G((完了・自動))
    end
    C -- 該当する --> F
```

- ポイントは、ゲートウェイの分岐で「どこまでがCS担当の仕事で、どこからシステムが自動で引き取るか」が一目でわかること。ここが文章の説明だけだと一番ズレやすい部分。
- ビジュアル版（記号の凡例つき）はClaudeのアーティファクトとして保存済み: https://claude.ai/code/artifact/66b5ffa3-ddbf-4de0-9963-9d02ab2e60fc

## 5. 作図ツールの選び方

| ツール | 特徴 | こんな時に |
|---|---|---|
| draw.io（diagrams.net） | 無料・オフライン可。公式BPMNシェイプ一式が標準搭載。Google Drive／ローカル／Confluenceどこにでも保存可能。 | 社内資料に1枚差し込む、という今回のような用途はこれで十分 |
| bpmn.io（Camunda） | BPMN 2.0仕様に厳密準拠。描いた図をそのままワークフローエンジンに読み込める。 | 業務フロー自体をシステムで自動実行させたくなった時 |
| Lucidchart／Miro | 複数人でのリアルタイム共同編集・コメントに強い。 | 打ち合わせをしながら複数人で同時に描きたい時 |
| PowerPoint／Googleスライド | 丸・四角・矢印だけで簡易的に代用。記法の厳密さはない。 | 正式な記法にこだわらず資料に1枚差し込めればいい時 |

- 結論: 今回のような社内共有目的ならdraw.ioで十分。左の図形パネル下部の検索窓に「bpmn」と入力すると公式シェイプが一式使えるようになる。

## 6. 描くときの4つのコツ

1. 最初から完璧を目指さない。主要な分岐が1〜2箇所あるくらいのシンプルな図で十分。細かい例外処理は後から足せる。
2. レーンは「誰が（何が）やるか」で分ける。「人」と「システム」で分けると業務側が知りたい境界線がそのまま図になる。
3. 矢印には条件をラベルとして書く（「該当する／しない」など）。後で見返した人も迷わない。
4. 描いたら関係者に見せて「ここは合ってますか」とすり合わせる。図を完成させることより、それを見せて会話することが本来の目的。

## 7. まとめ

- BPMNは、業務フローの認識ズレ（"ブランコの絵"のような伝言ゲーム）を防ぐための共通図式言語。
- 覚える記号は開始・終了・タスク・ゲートウェイの4つ＋レーンで、実務には十分。
- 作図ツールはdraw.ioで問題ない。CREからCSへの新システム紹介資料のように、「人の作業」と「システムの自動処理」の境界を示す場面で特に効果を発揮する。
