# 「確定した変更」と「まだ確定していない変更」が同じ作業ツリーに混在するときの分離方法（`git stash push -- <path>`）とdevice_bashでの削除権限の壁

- 学んだきっかけ: 9/1、Notion API検証で使った使い捨てシェルスクリプトを一般化したスニペットとして保存する一方、学習メモ本体だけを先にコミットしたいと思い、「特定のディレクトリだけをスタッシュし、残りをコミットする」という操作をCoworkに依頼して実際に行った際に、具体的な手順を確認した。

## 1. なぜ「全部stash」や「全部commit」では駄目だったのか

- 状況: 作業ツリーに、確定させたいファイル（学習メモ）と、まだコミットするか迷っている・整理中のファイル群（スニペット一式の入ったディレクトリ）が同時にuntrackedで存在していた。
- `git add -A && git commit` のように全部commitすると、まだ確定していない内容も一緒に履歴に残ってしまう。
- `git stash` を引数なしで実行すると作業ツリー全体が退避されてしまい、コミットしたいファイルまで消えてしまう。
- 欲しかったのは「特定のパス（ディレクトリ）だけを退避し、残りは作業ツリーに残す」という操作。

## 2. パスを指定してstashする（ディレクトリ単位のstash push）

`git stash push` はデフォルトで作業ツリー全体を対象にするが、コマンドの末尾に `--` を挟んでパスを指定すると、そのパス配下だけを対象にできる。

```
git stash push --include-untracked -- <ディレクトリ or ファイルパス>
```

ポイント:

- `--include-untracked` を付けないと、まだgit管理下にない新規ファイル（untracked）はstashの対象にならず、素通りしてそのまま作業ツリーに残ってしまう。「新規追加したディレクトリ」ごと退避したい今回のようなケースでは必須。
- `--` の後は複数パスを空白区切りで指定することもできる（git stashのパススペックとして一般的にサポートされている機能。今回は1ディレクトリのみで検証）。
- 退避後は `git status --short` で「指定したパス以外だけが残っている」ことを確認し、`git stash list` で `stash@{0}: WIP on <branch>: <直前のコミット> ...` の形でエントリができていることを確認すると安心。
- 退避した内容は消えたわけではなく、`git stash pop`（最新のstashを復元して削除）や `git stash apply`（復元するがstash自体は残す）でいつでも戻せる。今回は「今すぐ戻す必要はないが消したくもない」という状態だったため、popはせずそのまま保持した。

## 3. 残った分だけを通常通りコミットする

stashで対象パスを退避した後は、作業ツリーには「確定させたいファイル」だけが残っている状態になる。あとは通常のadd/commitで問題ない。

```
git add <残っているファイル>
git commit -m "<メッセージ>"
```

ファイル単位で `git add` すれば、うっかり他の変更を含めてしまう心配もなく、ここには特別な工夫は不要だった。

## 4. device_bash特有の壁: `.git/index.lock`の削除権限

`git stash push` を実行した際、`.git/index.lock` や `.git/objects/*/tmp_obj_*` のunlinkで `Operation not permitted` エラーが出て一度失敗した。

原因: device_bash（マウントしたフォルダに対するリモートのシェル実行）経由で操作していたが、そのサンドボックスは「マウントされたフォルダ内のファイル削除」をデフォルトで許可していない。gitは `index.lock` のような一時ファイルを自分で作成し、処理完了時に自分で削除する、という動作をするため、この「削除」権限がないとstash自体が完走できない。

対処の流れ:

1. 削除権限をリクエストする専用の許可フロー（対象フォルダと理由を明示し、ユーザーに承認してもらう）を経由して、そのフォルダでの削除操作を有効化する。
2. 承認された後も、いきなり `rm` はせず、ロックファイルが「本当に他のプロセスが使用中の実体のあるロックか」を確認する。具体的には次の2点をセットで見る。
   - `stat -c "%y" .git/index.lock` でロックファイルの更新時刻を確認する（直前の失敗した自分の試行によるものか、かなり古いものかを見る）。
   - `ps aux | grep -i git` 等で、そのリポジトリに対して実際に動いているgitプロセスがあるかを確認する。
   - 今回はロックの更新時刻が数十秒前で、かつ動いているgitプロセスが見つからなかったため、「直前の自分の失敗した試行が残した幽霊ロック」と判断できた。
3. 安全と判断できてから `rm -f .git/index.lock` で削除し、`git stash push` を再実行する。

これは[8/2に別件で調査した「幽霊ロック」の話](2026-08-02-git-index-lock-auto-commit-failure.md)と同種の問題で、「タイムスタンプの新しさ」と「実際に動いているプロセスの有無」をセットで確認してから削除するという判断基準がそのまま再利用できた。

## まとめ

- 作業ツリーに「確定させたい変更」と「まだ確定していない変更」が混在している場合、`git stash push --include-untracked -- <path>` のようにパスを指定すれば、対象を絞って退避できる。作業ツリー全体をstashしたりcommitしたりする必要はない。
- 退避した内容は `stash@{0}` のような形でスタック的に保持され、`git stash pop`/`apply` で後から復元できるので、「今は確定させたくないが消したくもない」という状態を安全に作れる。
- リモート環境（今回はdevice_bash）でgit操作をする場合、サンドボックスのファイル削除制限によって `.git/index.lock` のような内部的な一時ファイルの後片付けそのものがブロックされることがある。その際は「タイムスタンプの新しさ」と「実際に動いているプロセスの有無」を確認してから削除するという、[過去の幽霊ロック調査](2026-08-02-git-index-lock-auto-commit-failure.md)と同じ判断基準が使える。
