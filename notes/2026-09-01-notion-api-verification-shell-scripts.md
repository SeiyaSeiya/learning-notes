# Notion API連携の実装検証で使った「使い捨てシェルスクリプト」パターンと、存在しないプロパティ名を渡した際の実際の挙動

- 学んだきっかけ: GASプロジェクトとNotion連携実装で、実装を依頼したClaude Codeのセッションから何度か「これを実行してください」という短いシェルスクリプトを渡され、その理由と一般的な考え方をChatで確認した。

## 1. なぜClaude Codeがシェルスクリプトの実行を依頼してくるのか

- Claude CodeはローカルのGitリポジトリ上で作業しているが、Notion API連携の実装にはNotion Integration TokenとNotionの実際のデータベーススキーマ（プロパティ名・型・選択肢一覧）が必要になる。
- トークンはGASのスクリプトプロパティにしか保存されておらず、Claude Code自身はGASのスクリプトプロパティを直接読む手段を持っていない（`clasp run`でGAS側の関数を呼び出す方法自体はあるが、実行API有効化・専用クレデンシャルの取得など大掛かりな一度限りの準備が必要で、今回はその選択はしなかった）。
- そこで「自分（人間）が手元でトークンを一度だけ入力し、その場でAPIを叩いて結果だけをファイルに保存する」という短いスクリプトを用意してもらい、実行結果（JSON等）だけをClaude Codeに渡す、という役割分担になった。トークンそのものはClaude Codeにも見せない。

## 2. 使い捨てシェルスクリプトの型

今回渡された3種類のスクリプトは、いずれも同じ型に当てはまる。

1. **スキーマ取得**（`notion_schema.sh`）: プロパティ名・型・選択肢一覧を確認する。
2. **疎通確認**（`notion_e2e_check.sh` / `.js`）: 実際に1件テストページを作成し、想定した値が正しく入るかを検証する（確認後は手動で削除する運用）。
3. **未知の挙動の実測**（`notion_unknown_prop_probe.sh`）: 公式ドキュメントに書かれていない仕様（存在しないプロパティ名を渡すとどうなるか）を、実際にAPIを叩いて確認する。

共通する作法:

- `set -e` を先頭に入れ、途中のコマンドが失敗したら即座に停止させる。
- トークンは `read -rs` で非表示入力にし、環境変数経由でNode/curlに渡す。コマンドの引数や設定ファイルへ直接書かない（シェル履歴にも残さない）。
- 実行結果は同じディレクトリのJSONファイルに書き出し、後でClaude Code側がそれを読み込んで実装の判断材料にする。
- 検証用に作成したページは自動でゴミ箱へ移動させる、あるいは「確認後に手動で削除してください」と明示する（本番データに紛れ込まないようにする配慮）。

## 3. 実測で分かったNotion APIの挙動

- 存在しないプロパティ名を`properties`に渡すと、**サイレントに無視されるのではなく、HTTP 400（`validation_error`）で拒否される**ことを実機で確認した（公式ドキュメントには明記されていなかった）。
- つまり、Notion側でプロパティ名が変更・削除されると、それ以降のページ作成は**1件も成功しなくなる**（一部の項目だけ抜けるのではなく全滅する）。この実測結果が根拠になり、実装側で「事前にスキーマの変化（プロパティの削除・型変更・表記の微妙な違いなど）を検知してSlack通知する」という安全策を追加する判断につながった。
- 一方、選択肢（セレクト/マルチセレクト）の値が既存の選択肢と一致しない場合は、そのプロパティだけが空欄になるだけで、ページ作成自体は失敗しない（他の項目は問題なく登録される）。
- この2つの違いから、「プロパティ名のズレ＝影響範囲が全件に及ぶので即Slack通知」「選択肢の不一致＝影響範囲がその1項目に留まるのでログのみで通知は不要」という運用判断ができた。ドキュメントに書かれていない仕様は、影響範囲が大きい場合は推測で実装せず、使い捨てスクリプトで実際に1回試してから設計判断をするのが確実。

## 4. Notion APIの一般的な使い方（今回わかった要点）

- すべてのリクエストに`Authorization: Bearer <トークン>`と`Notion-Version`ヘッダーが必要（バージョン省略は避ける。古いデフォルトバージョンで動いてしまう）。
- 2025-09-03のバージョンから「データソース」という階層がデータベースの下に追加され、`database_id`だけでは直接ページを作成できなくなった。手順は次の2段階。
  1. `GET /v1/databases/{database_id}` を叩き、レスポンスの`data_sources[0].id`を取得する。
  2. その`data_source_id`を`POST /v1/pages`の`parent`に指定してページを作成する（`{"type": "data_source_id", "data_source_id": "..."}`。古い`{"type": "database_id", ...}`は使えない）。
- プロパティのスキーマは`GET /v1/data_sources/{data_source_id}`で取得できる（プロパティ名・型・選択肢一覧はここで確認する。推測でハードコードしない）。
- プロパティの値は型ごとに決まった入れ子のJSON構造で渡す必要がある（例: セレクト型は`{"select": {"name": "..."}}`、テキスト型は`{"rich_text": [{"text": {"content": "..."}}]}`）。渡し方を間違えると値が入らない、あるいは型が変わったことに気づかず値が入らなくなる、という事故が起きるため、値を送る直前に型もスキーマから確認する実装にしておくと安全。

## まとめ

- 秘匿情報が絡む外部API連携の実装では、AIエージェント（Claude Code）自身にトークンを渡さず、人間が手元で一度だけAPIを叩いて結果（スキーマ等の非秘匿情報）だけを渡す、という分担が安全かつ実用的。
- ドキュメントに書かれていない仕様（今回は「存在しないプロパティ名を渡した場合の挙動」）は、影響範囲が大きい場合は推測で実装を進めず、使い捨てスクリプトで実際に1回試してから設計判断（通知の要否など）をするのが確実。
