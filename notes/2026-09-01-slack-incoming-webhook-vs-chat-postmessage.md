# Slackの「Incoming Webhookでの投稿」と「chat.postMessageでの投稿」の違い、および「メッセージの更新」に2種類ある話

- 学んだきっかけ: GASのVOC登録リマインド機能（③）の設計中、「リマインドのDMに、該当するSlack投稿への直接リンクを載せたい」という要件から、既存のボタン付き投稿（Incoming Webhook経由）を`chat.postMessage`に切り替える必要が出てきた。その理由をCoworkに確認していく過程で、「でも登録ボタンを押した後、既存の投稿はちゃんと編集されているじゃないか」という点で一度混乱した。

## 1. そもそもの前提: Slackで「1件のメッセージ」を指すには何が必要か

Slack APIの世界では、特定の1件のメッセージは **`channel`（チャンネルID）と`ts`（投稿されたタイムスタンプ）のペア** で識別される。パーマリンク（`https://xxx.slack.com/archives/C0123/p...`）も、この2つの値さえあれば`chat.getPermalink`というAPIがSlack側で組み立てて返してくれる。逆に言うと、**この2つの値を知らない限り、パーマリンクは作れない**。

## 2. Incoming Webhookは「投げっぱなし」の仕組み

Incoming Webhookは、決められたURLにJSONをPOSTすると指定チャンネルへ投稿される、投稿専用のシンプルな仕組み。投稿が成功しても、レスポンスは`"ok"`という文字列だけで、**今投稿したメッセージの`channel`・`ts`を一切教えてくれない**。これはバグではなく、「通知を投げっぱなしにする」用途に割り切った設計。かつ、後からその値を別の手段で取得することもできない。

たとえるなら、Incoming Webhookは「郵便ポストに手紙を投函する」ようなもの。投函できたことは分かる（`"ok"`）が、その手紙がどの棚の何番目に置かれたかという受領証はもらえない。

## 3. chat.postMessageは受領証（channel + ts）をくれる

`chat.postMessage`はBotトークンを使って直接メッセージを送るAPIで、成功時のレスポンスに投稿した`channel`と`ts`がそのまま含まれる。この2つを保存しておけば、`chat.getPermalink`（**追加スコープ不要**、`channel`と`message_ts`だけで呼べる）でいつでもパーマリンクを作れる。

## 4. 個人的に詰まった点: 「後から編集できない」はずなのに、なぜボタン押下後の差し替えは動いているのか

既存の実装（VOC登録UIのステップ①）では、Incoming Webhookで投稿したメッセージに対して、ボタン押下後に「✅ 対応済み」への差し替えが実際に行われている。「Incoming Webhookは後から編集できない」という説明と矛盾するように見えたが、これは**Slackにおけるメッセージ更新の方法が実は2種類ある**ことを理解していなかったのが原因だった。

### ① `response_url`（既存実装が使っている方法）

ボタンが押されたときやモーダルが送信されたとき、Slackが送ってくる`block_actions`/`view_submission`ペイロードの中に、**Slackが自動的に発行する一時的な専用URL**（`response_url`）が入っている。このURLに`replace_original: true`を付けてPOSTすると、「その操作が発生した元のメッセージ」をSlack側が内部的に特定して更新してくれる。**アプリ側は`channel`や`ts`を一切知らなくていい**のがポイントで、元のメッセージがIncoming Webhookで投稿されたものであっても成立する。

ただし制約が大きい: **発行から一定時間（目安30分）・回数（目安5回程度）で失効**し、かつ「今まさに起きた操作」に紐づいた形でしかもらえない。何日も経ってから「あのメッセージ用に`response_url`をもう一度発行してほしい」と後から取得することはできない。

### ② `channel` + `ts`（chat.update・パーマリンク生成に使う方法）

投稿時点で`channel`と`ts`を自分たちで記録しておき、それを使って**いつでも**（何日後でも）そのメッセージを更新したり、リンクを作ったりする方法。Incoming Webhookはこの2つを返さないため、この方法は使えない。

### この2つの違い

| | ①`response_url` | ②`channel`+`ts` |
|---|---|---|
| 入手できるタイミング | ボタン押下・モーダル送信などの対話イベント発生時のみ | 投稿（`chat.postMessage`）成功時 |
| 有効期限 | 短い（目安30分・5回程度） | 無期限（保存しておけば何年後でも使える） |
| Incoming Webhook投稿でも使えるか | 使える | 使えない（`chat.postMessage`が必要） |
| 用途 | その場での即時の1回限りの更新 | 後日の更新・パーマリンク生成など、時間差のある用途 |

## まとめ

- Slackで特定のメッセージを指す・後から扱うには`channel`+`ts`が必要で、これはIncoming Webhookのレスポンスには含まれない（`chat.postMessage`のレスポンスには含まれる）。
- 「メッセージを後から更新する」という現象だけを見ると同じに見えるが、実際には「対話イベントに紐づく一時的な`response_url`」と「`channel`+`ts`を使った永続的な方法」という**まったく別の仕組み**が存在する。片方（`response_url`）が使えているからといって、もう片方（`channel`+`ts`を使う用途、パーマリンク生成など）も自動的に使える、というわけではない。
- 「時間差がある（数日後にリマインドする、など）」用途では`response_url`は原理的に使えないため、投稿時点から`channel`+`ts`を記録しておく設計に変える必要がある、という結論になった。
