# 既にpush済みのコミットを書き換える際の安全な手順（fetchで確認→必要ならcherry-pick→`--force-with-lease`）

- 学んだきっかけ: learning-notesリポジトリのコミットメッセージに含めた`Co-Authored-By`行が、GitHub上で「co-author」として表示されてしまい、これを消すために既にpush済みのコミットを`amend`して上書きした。その際に`git push --force-with-lease=`が一度拒否され、原因を切り分けながら安全に上書きするまでの一連の作業から、一般的な手順として整理した。

コミットの直し方自体（`amend`/`rebase -i`）や、force pushの基本的な注意点（ダングリングコミットとして残る、認証情報漏洩時はローテーションが必要、サンドボックス環境ではSSH鍵が無くpushできないことがある）は[2026-07-30のメモ](2026-07-30-git-commit-history-rewrite-amend-rebase-cherrypick.md)に既にまとめてある。今回はその続き、**「pushする前に何を確認すべきか」「拒否されたときにどう切り分けるか」**を中心にまとめる。

## 1. なぜ一手間かけて確認する必要があるのか

`amend`や`rebase`で書き換えたいコミットが、既にリモートへpush済みの場合、ローカルとリモートはその時点から別物（同じ内容でも別のSHA）として枝分かれする。ここで単純に上書きpushすると、**自分がamendしている間にリモート側で誰か（あるいは自動化スクリプトなど）が新しいコミットを積んでいた場合、それを消してしまう**リスクがある。今回のリポジトリは[launchdによる自動commit・push（6:30/18:30）](2026-07-14-launchd-auto-commit.md)が設定されているため、この手のリスクが現実に起こり得る環境だった。

## 2. 手順: 書き換え → fetch → 確認 → （必要なら載せ替え）→ force-with-lease

1. 直したいコミットを`amend`（または`rebase -i`）で書き換える。
2. **pushする前に必ず`git fetch`する。** 自分が書き換えている間にリモートが進んでいないかを確認するため。
3. `git log --oneline <書き換え前の元コミットのSHA>..origin/<ブランチ名>`で、リモートに「自分が知らない新しいコミット」が無いか確認する。
   - 何も表示されなければ、リモートは書き換えた地点のまま進んでいない。そのまま次へ進んでよい。
   - 何か表示された場合、それを失うわけにはいかないので、`git cherry-pick <元コミットのSHA>..origin/<ブランチ名>`で、書き換え後の自分のコミットの上にその新しいコミットたちを載せ替えてからpushする。
4. `git push --force-with-lease origin <ブランチ名>`でpushする。

## 3. `--force`ではなく`--force-with-lease`を使う

`--force`は「リモートが今どうなっていようと問答無用で上書きする」オプション。`--force-with-lease`は「自分が最後に`fetch`した時点のリモートの状態と、実際の今のリモートの状態が一致しているときだけ上書きを許可する」という安全装置付きのオプション。書き換えたコミットをpushする際は、基本的に常に`--force-with-lease`を使い、素の`--force`は避けるのが安全（気づかず誰か・何かの作業を消してしまう事故を防げる）。

## 4. 今回の落とし穴: 「拒否された＝リモートが進んでいる」と決めつけない

今回、`git push --force-with-lease=`（末尾に値を付けずに実行）が`non-fast-forward`で拒否された。この時点では「自動commitスクリプトがリモートに新しいコミットを積んだのだろう」と推測したが、実際に`git fetch`＋`git log --oneline <元コミット>..origin/main`で確認したところ、**リモートには書き換え前のコミットの上に何も積まれていなかった**。つまり原因は「リモートが実際に進んでいた」ことではなく、**`--force-with-lease=`という書き方（`=`の後に値が続いていない）自体が悪さをしていた**可能性が高いという結論になった（素の`--force-with-lease`に書き直したところ問題なく成功した）。

ここでの教訓は、「pushが拒否された」という現象だけから原因（今回なら「自動commitと衝突した」）を決めつけず、**`fetch`＋`log`で実際に何が起きているかを毎回確認してから対応する**、ということ。決めつけて`cherry-pick`などの余分な手順を踏んでも実害は無いが、逆に「実は何も進んでいないのに何かが進んだと思い込む」ような誤った原因特定は、次回以降の判断を誤らせる。

## まとめ

- 既にpush済みのコミットを書き換える場合、**必ず`fetch`してからリモートの状態を確認**し、リモートに新しいコミットがあればそれを`cherry-pick`で保持してから上書きする。
- 上書きには素の`--force`ではなく`--force-with-lease`を使う。
- pushが拒否されたときは、原因を推測だけで決めつけず、`fetch`＋`log`で実際の状態を確認してから対応する。今回は「自動commitと衝突した」という推測が誤りで、実際には`--force-with-lease=`という書き方自体が原因だった。
