# gitのfast-forwardマージと`--ff-only`（worktreeで作ったコミットを本体に取り込む場面）

- 学んだきっかけ: Claude Codeに依頼した修正がworktree側のブランチでcommitされたが、本体のディレクトリ（`main`をチェックアウト中）でログを見てもそのcommitが見当たらず、「本当にcommitされているのか」を確認するところから、取り込みコマンドとして案内された`git merge --ff-only`の意味を調べた。

worktreeとcheckoutの違い自体は[2026-07-09のメモ](2026-07-09-git-worktree-and-checkout.md)にまとめてある。今回はその続きで、**worktree側のブランチに溜まったcommitを本体（`main`）へ取り込むとき**に使うマージの話。

## 1. 「commitしたのに見当たらない」の正体

worktreeは同じ`.git`を共有しつつ、別ディレクトリに別ブランチを展開したもの。そのため、

- worktree側でcommitされる先は`claude/xxx`のような**作業用ブランチ**
- 本体のディレクトリはずっと`main`をチェックアウトしたまま

となり、本体で`git log`しても作業用ブランチのcommitは出てこない。**commitが無いのではなく、今見ているブランチに無いだけ**。確認は次のコマンドでできる。

```bash
# ブランチ一覧（+ が付くのは別worktreeでチェックアウト中のブランチ）
git branch

# main に無くて作業用ブランチにだけあるcommitを一覧
git log --oneline main..<作業用ブランチ名>

# 中身を確認
git show <作業用ブランチ名>
```

`main..<ブランチ>`という書き方は「左側には無くて右側にはあるcommit」を意味する。ここに出てきたcommitが、これから取り込む対象。

## 2. fast-forwardとは

取り込み元のブランチが、取り込み先のブランチの**先端からまっすぐ伸びているだけ**の状態を指す。

```
main:           A
作業用ブランチ:  A ─ B
```

`main`はAにいて、作業用ブランチはそこから1つ進んだB。**`main`側には独自のcommitが1つも無い**。この場合、gitは履歴を「合流」させる必要がなく、`main`というブランチのポインタをAからBへ**前にスライドさせるだけ**で取り込みが完了する。これがfast-forward。

- 履歴は一直線のまま
- マージcommitは作られない

逆に、こちらも進んでいた場合はfast-forwardできない。

```
main:           A ─ C
作業用ブランチ:  A ─ B
```

この形だとポインタを進めるだけでは済まず、BとCを合流させる**マージcommit**を作る必要がある。

## 3. `--ff-only`の挙動

| コマンド | 動作 |
|---|---|
| `git merge <ブランチ>` | fast-forwardできるならそうする。できなければ自動でマージcommitを作って合流する |
| `git merge --ff-only <ブランチ>` | fast-forwardできるときだけ実行する。できなければ**何もせずエラーで止まる** |
| `git merge --no-ff <ブランチ>` | fast-forwardできる場合でも、あえてマージcommitを作る |

`--ff-only`で止まるときのメッセージ。

```
fatal: Not possible to fast-forward, aborting.
```

## 4. なぜ`--ff-only`を付けるのか

一種の**安全装置**として使う。

`--ff-only`を付けずにマージすると、もし自分が把握していない間に`main`側にも別のcommit（別セッションの作業、自動commitスクリプトなど）が入っていた場合、gitは黙ってマージcommitを作って合流させてしまう。処理としては正しいが、**「今の`main`は自分が作業を始めた時点のままだ」という前提が崩れていたことに気づけない**。

`--ff-only`を付けておけば、そういう想定外の状態のときは何も起きずに止まるので、その場で気づける。止まったら状況を確認したうえで、

- `git merge <ブランチ>`（オプション無し）でマージcommitを作って合流させる
- あるいは作業用ブランチを`git rebase main`してから改めてfast-forwardで取り込む

のどちらかを、**意識的に選ぶ**ことになる。「気づかずに合流していた」と「確認したうえで合流させた」の差が、このオプションの価値。

前に整理した[`--force-with-lease`](2026-09-02-git-rewrite-already-pushed-commit-safely.md)と発想が同じで、どちらも「自分が想定している状態と実際の状態が一致しているときだけ実行を許す」タイプの安全装置になっている。

## 5. デフォルト挙動を変える設定

毎回オプションを付けるのが面倒な場合、設定でデフォルトにできる。

```bash
# fast-forwardできないマージは常に拒否する
git config --global merge.ff only
```

`pull`にも同種の設定がある（`pull.ff only` / `pull.rebase true`）。意図しないマージcommitで履歴が汚れるのを避けたい場合によく使われる。

## 6. 実際の取り込みの流れ

worktreeで作業→本体に取り込む→デプロイ、という一連の流れは次のようになる。

1. worktree側で作業しcommitする（ブランチは`claude/xxx`など）
2. 本体のディレクトリに戻り、`git log --oneline main..<ブランチ>`で取り込む内容を確認する
3. `git merge --ff-only <ブランチ>`で`main`に取り込む
4. デプロイ系のコマンドを本体のディレクトリから実行する

4が地味に重要で、**デプロイ用の設定ファイルが本体のディレクトリにしか無い場合**（worktree側には展開されない、あるいは無視される設定になっている場合）、取り込みを済ませないと古いコードがデプロイされる。「commitしたのにデプロイ結果に反映されない」という混乱はここで起きやすい。

## まとめ

- worktreeでcommitされたものが本体で見えないのは正常。ブランチが違うだけなので、`git log --oneline main..<ブランチ>`で確認する。
- fast-forwardは、取り込み先に独自のcommitが無いときにブランチのポインタを前に進めるだけで済むマージ。マージcommitは作られず履歴は一直線のまま。
- `--ff-only`は「fast-forwardできるときだけマージする」オプション。できない＝自分の知らない変更が入っているということなので、そこで止めて気づけるようにする安全装置として使う。
- 止まった場合は、状況を確認したうえでマージcommitを作るかrebaseするかを意識的に選ぶ。
