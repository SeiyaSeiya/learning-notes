# READMEの書き方：読みやすいドキュメントのためのベストプラクティス

- 学んだきっかけ: READMEを詳細に書いた経験がなく、「綺麗なドキュメントを書くには何に気をつければよいか」をClaudeに質問して整理した。

## 1. 基本の考え方

- READMEは「最初の5分で読者に判断（使うか・使わないか）と行動（動かす）をさせる」ための文書。
- 読者は主に3種類：利用者 / コントリビューター / 将来の自分やチームメンバー。全員に向けると散漫になるので、**メインの読者を一人決め**、他は`CONTRIBUTING.md`や`docs/`に逃がす。

## 2. 基本構成（上から重要度が高い順）

1. プロジェクト名と一行説明（「何をするものか」を一文で）
2. バッジ（任意。CI状況・ライセンス・バージョンなど）
3. 背景・特徴（なぜ必要か、何ができるか）
4. スクリーンショット／デモ
5. 前提条件（OS、言語バージョン、依存ツール）
6. インストール（コピペで動くコマンド）
7. 使い方（Quick Start。最小の動く例を先に、詳細は後）
8. 設定・環境変数（表形式が見やすい）
9. 開発者向け情報（テスト、ディレクトリ構成、ビルド）
10. コントリビュート方法／サポート窓口
11. ライセンス
12. ロードマップ・既知の問題（任意）

- 小さなプロジェクトなら全部は不要。**「説明・インストール・使い方・ライセンス」の4つ**があれば最低限成立する。

## 3. 書き方のコツ

- **逆三角形で書く**: 結論・目的を先頭に、細部は下に。
- **動く最小例を早く見せる**: 読者が成功体験を得るまでの時間を短くする。
- **コードブロックは実際に動くものを**: 言語を指定（```bash など）し、コピペで動くことを確認する。
- **一つの見出しに一つの話題**: 見出し階層は`#`〜`###`程度に留める。
- **長くなったら分割**: 目次を付けるか、詳細は`docs/`へ移してリンクする。
- **相対リンクを使う**: ブランチやフォークでも壊れにくい。
- **専門用語・略語は初出で説明する**。
- **言語を決める**: OSSなら英語、社内ツールなら日本語が一般的。多言語なら`README.ja.md`のように分ける。

## 4. よくある失敗

- インストール手順が古く、実際には動かない
- 「何のためのものか」が書かれていない
- 前提条件（バージョン等）の記載漏れ
- 巨大な一枚岩になって誰も読まない
- 更新されず放置される（日付やバージョンを明記すると鮮度が分かる）

## 5. 品質を保つ運用のコツ

- **クリーンな環境で手順を試す**: 新しいマシンやDockerコンテナで、READMEだけを頼りにセットアップしてみる。
- **他の人に読んでもらう**: 書いた本人は前提知識があるため抜けに気づきにくい。
- **コード変更と同時に更新する**: PRのチェックリストに「READMEの更新」を入れる。
- **リンク切れチェックやMarkdown lintをCIに入れる**（`markdownlint`など）。

## 6. 最小テンプレート

````markdown
# プロジェクト名

一行で何をするものか。

## 特徴
- 特徴1
- 特徴2

## 必要環境
- Python 3.11+

## インストール
```bash
git clone https://github.com/xxx/yyy.git
cd yyy
pip install -r requirements.txt
```

## 使い方
```bash
python main.py --input sample.txt
```

## 設定
| 変数名 | 説明 | デフォルト |
|---|---|---|
| `API_KEY` | APIキー | なし |

## 開発
```bash
pytest
```

## ライセンス
MIT
````
