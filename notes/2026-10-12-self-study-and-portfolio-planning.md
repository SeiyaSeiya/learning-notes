# 自己学習とポートフォリオが進まないときの考え方と、題材・進め方の整理

- 学んだきっかけ: 「自己学習はやりたいことが不明瞭」「ポートフォリオは作りたいものがない」という悩みをClaudeに相談した際のメモ。
- 注意: 書籍名・データ提供状況などはClaudeの知識や簡易検索に基づく。利用前に公式情報で要確認。

## 1. 悩みの捉え直し

* 目標を先に決めて逆算する型でなくても、「困りごとが出て調べて形にする」課題駆動の学習で十分続いている（learning-notesの蓄積がその証拠）。
* ただしメモがClaudeとのやり取りの記録中心だと、体系的な理解や再現できる力にはつながりにくい（学習効果が薄いという自己評価はもっとも）。
* 対策: メモは回答の要約ではなく、何も見ずに自分の言葉で説明を書き、そのあと答え合わせする形にする。
* 学習は義務感より興味を優先した方が続く。現在の興味は **OS自作・ネットワーク・コンテナ**。

## 2. 「Claudeに案を出させて実装する」進め方のコツ

* 条件なしで案を出させると無難な案（ToDoアプリ等）になる。**材料を渡す**: 日常の面倒ごと、触っている技術、使える時間、見せたい相手。
* 案は10個程度出させ、実現性と見せ場も評価させる。最終判断は「自分が実際に使うか」。
* **役割分担**: 設計は自分で考えてClaudeにレビューしてもらう／コードは自分で書き、詰まったときだけ聞く。丸ごと任せるとポートフォリオが「Claudeに作らせた成果物」になる。
* 作り終えたら「なぜこの設計にしたか」を自分の言葉でREADMEに書く。

## 3. 題材の候補

### バス時刻アプリ
* スクレイピングの前に、**オープンデータ（GTFS-JP等）や公式APIがないか**を先に調べる。
* スクレイピングする場合は、利用規約・robots.txtの確認、アクセス間隔、キャッシュ（負荷をかけない）が必要。法的判断は個別事情による（Claudeは法律の専門家ではない）。
* 手順: 事業者・路線を決める → オープンデータ有無を調べる → 規約確認 → `requests` + `BeautifulSoup`で取得 → JSON保存 → 「次のバスは何分後か」を計算 → CLI/Web/Slack通知へ。
* 自由に使えるデータの例: e-Stat API（人口など。アプリケーションID登録が必要）、気象庁データ、自治体のオープンデータ（ゴミ収集日・避難所など）。

### 他の案（学べる技術別）
* API・バックエンド: FastAPIのミニAPI、URL短縮サービス
* データ: 公開データの収集→蓄積→可視化パイプライン、家計集計ツール
* 自動化・運用: 通知bot、GitHub Actionsでのテスト・デプロイ
* 設計・テスト: 既存自作スクリプト（pull-all-reposなど）のリファクタリング、pip配布できるCLI
* メンタル状態の記録アプリ: ローカルSQLiteで完結、CLIで数秒で記録、1〜2週間使ってから集計を足す。データは`.gitignore`で公開しない（デモは架空データ）。自分用の記録ツールと位置づけ、医療的判断はしない旨をREADMEに明記。

### 選ぶ基準
1. 自分が実際に使う  2. 学びたい技術が1〜2個はっきりしている  3. 2〜3週間で動くものまで作れる大きさ

## 4. 構成の考え方

* **APIの実装内容がスクレイピング**というケースはよくある。利用者は自作APIを呼ぶだけで、裏側でページ取得→HTML解析→JSON化している。HTML変更時の修正がAPI内側で済む。
* 呼ばれるたびに相手サイトを取りに行かない。**定期バッチで取得して保存し、APIは保存分を返す**（キャッシュ）のが実運用の形。
* 自作APIを核に、CLI・Webフロント・Slack通知など複数クライアントをぶら下げられる。ロジックが1か所に集まる（責務分離）。
* 順番: API（テスト付き）→ CLI → Web/通知。各段階で「一応使える」状態にしておく。
* スクレイピングデータを返すAPIを公開・再配布する場合は規約・著作権により慎重に。ポートフォリオではコードだけ公開し、データ取得は各自に任せる形が無難。

## 5. 興味のある3テーマの関係と学び方

* OS → プロセス・メモリ・ファイルシステム。コンテナの実体はLinuxの機能（namespace／cgroups／chroot等）の組み合わせ。ネットワークはコンテナの通信理解にも効く。
* 読むより**小さく作る**:
  * コンテナ: unshare・chroot・cgroupsで自作コンテナ（プロセス隔離して`/bin/sh`を動かすところまで）
  * ネットワーク: ソケットでTCPサーバー → 簡易HTTPサーバー → Wiresharkでパケット観察
  * OS: 『30日でできる！OS自作入門』『ゼロからのOS自作入門』（難易度高め）
* 3つ同時でなく1つに絞る。コンテナから入るのが手応えと範囲のバランスが良い。

## 6. 車輪の再発明

* **学習目的なら有効**: 隠されていた複雑さ・設計判断の理由が分かり、使うときの精度も上がる。
* **実務・プロダクトでは基本避ける**: 既存品は検証・バグ修正・セキュリティ面で鍛えられている。認証・暗号のような領域は自作しない。
* コツ: 学習用と割り切る／作った後に本物と比べて足りない点を調べる／「何を理解したいか」を先に決める。
* ポートフォリオに載せるなら「学習目的・本番利用は想定外」と明記し、学んだことと本物との違いを書く。

## 7. 技術選定の理由を残す

* 「流行っているから」「Claudeに勧められたから」ではなく、**要件との適合・比較した選択肢・自分の事情・トレードオフ**で説明する。
* READMEや`docs/decisions.md`に、ADRを軽くした形で残す:

  ```
  ## DB: SQLite を採用
  - 背景: 利用者は自分1人、データは数千件程度
  - 検討した選択肢: SQLite / PostgreSQL
  - 決定: SQLite（セットアップ不要でバックアップもファイル1つ）
  - トレードオフ: 同時アクセスに弱い。複数人で使うなら移行を検討
  ```
* 後から変更してもよい。「Xにしたが問題が出てZに変更した」記録は成長の証拠になる。
* 実装前に、言語・フレームワーク・DB・実行環境・テストの5項目を一覧にして決める。

## 8. 次の一歩

* 普段使うバス事業者・路線を決め、オープンデータの有無を調べる → APIの仕様を文章で下書きする（Claudeにレビューしてもらう）。
* 興味3テーマのうち最初に取り組むものを1つ決める。
