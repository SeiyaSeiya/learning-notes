# RailsのSidekiqによる非同期処理の設計パターン（一括処理・進捗管理・リトライ）

- 学んだきっかけ: 業務で関わっている大規模なRails APIプロジェクトのワーカー実装・設定・呼び出し側のコードを読み、次の職場のRails開発でも通用する設計の勘所としてClaude（Cowork）と整理した。社内固有の名称は含めず、一般化した内容だけを残す。
- 関連メモ: [マイグレーションと大規模DB](2026-11-27-rails-migration-and-large-db-handling.md) / [N+1対策とパフォーマンス改善](2026-11-27-rails-n-plus-one-and-performance-patterns.md)

## 1. 結論

非同期処理で押さえるのは次の6点。

1. 一括操作は「1件につき1ジョブ」に分け、引数はIDとプリミティブ値だけにする
2. 進捗を見せるには、Batchの機能より**親子テーブル＋ステータス＋エラー保存**のデータ設計が本質
3. リトライ方針はジョブの性質で明示的に決める（デフォルトは約25回・数週間）
4. キューは処理の種類で分け、並列数はDB接続プール以下にする
5. 運用はWeb用とWorker用でプロセスを分け、例外・メトリクスを監視する
6. テストは「投入されたこと」と「ジョブ単体の振る舞い」を分けて確認する

## 2. 題材プロジェクトの特徴（一般化）

| 観察 | 内容 |
| --- | --- |
| ワーカー数 | 約18個。ほぼすべてが一括更新・削除・コピー系 |
| 書き方 | `include Sidekiq::Worker`（Sidekiq直接）。Active Jobはほぼ未使用 |
| キュー | 処理の種類ごとに専用キュー（約15本）を `config/sidekiq.yml` に列挙 |
| 並列数 | 環境変数で指定、既定は30 |
| リトライ | 一括系は `retry: 0`、イベント記録系は `retry: false` |
| 進捗管理 | Sidekiq Pro の Batch ＋ 自前の管理テーブル2つ ＋ `sidekiq-status` |
| テスト | `Sidekiq::Testing.fake!` ＋ 各テスト前に `clear_all` |
| 運用 | Web用とWorker用でDockerfile・ビルド設定を分離。CloudWatch・Sentry連携 |

## 3. 各ポイントの解説

### 3-1. 一括操作は「1件1ジョブ」、引数はシンプルな値だけ

```ruby
batch.jobs do
  ids.each { |id| jid = Worker.perform_async(id, params_json, params) }
end
```

- 1件失敗しても他の件に影響せず、失敗した対象だけを特定できる。
- 引数はID・JSON文字列・ハッシュなどのシンプルな値。ActiveRecordオブジェクトは渡さない（Sidekiqは引数をJSONにしてRedisに保存するため）。`Sidekiq.strict_args!` を有効にすると、この規律を強制できる。
- ジョブの中で最新のレコードを再取得する。

### 3-2. 進捗管理：Batch ＋ 自前の親子テーブル

- `Sidekiq::Batch` と `batch.on(:complete, Worker, ...)` で、全ジョブ終了時にコールバックを呼ぶ。
- 加えて、親テーブル（バッチ単位）と子テーブル（ジョブ単位）を自前で持つ。
  - 子テーブルには、対象ID、対象名、ステータス（queued / working / complete / failed）、エラー内容を保存する。
- 進捗確認APIでは `Sidekiq::Status.get_all(jid)` でジョブごとの状態を返す。
- **Batch は Sidekiq Pro（有償）の機能**。OSS版では使えない。
  - 代替は、自前テーブルで総数・完了数・失敗数を管理し、各ジョブの最後に原子的にカウントを更新する方法など。
  - 本当に持ち帰るべきなのは、Batchの使い方より「ユーザーに進捗を見せるためのデータ設計」。

### 3-3. リトライ方針

- 一括更新系は `retry: 0`。人が操作した結果の処理で、途中まで成功した状態でのリトライは二重実行・不整合のリスクがあるため、失敗は記録して人に見せる。
- イベント記録系は `retry: false`。失敗しても影響が小さく、デッドキューに溜めたくないため。
- Sidekiqのデフォルトは**最大25回、数週間にわたるリトライ**。副作用のあるジョブでは明示的に決める。
- リトライを許すなら、ジョブは**冪等**（何度実行しても同じ結果）に作る。
  - 例: 送信済みフラグ、`find_or_create_by`、一意制約で二重登録を防ぐ。
- `sidekiq_retries_exhausted`（リトライ尽き時のフック）や `sidekiq_retry_in`（独自バックオフ）で、方針を細かく制御できる。

### 3-4. キュー設計と並列数

- 処理の種類ごとにキューを分けると、重い処理が軽い処理を詰まらせるのを防げる。
- 並列数（`concurrency`）は、**DBの接続プール（`database.yml` の `pool`）以上にしない**。並列30ならプールも30以上が必要。
- キューを重みなしで列挙したときの処理順（厳密な優先順位か、重み付きか）は、使うバージョンの公式ドキュメントで確認する。

### 3-5. 運用まわり

- Web用とWorker用でプロセスを分けてデプロイする（`sidekiq -C config/sidekiq.yml`）。
- 例外はSentry等で拾い、キュー滞留などのメトリクスはCloudWatch等で監視する。
- Redisの名前空間は `redis-namespace` で環境ごとに分けていたが、これは **Sidekiq 7 で非対応**。Sidekiq 7以降では、Redisのdb分離や別インスタンスなどで環境を分ける。

### 3-6. テストの定石

```ruby
Sidekiq::Testing.fake!        # perform_async は実行せずキューに積むだけ
Sidekiq::Worker.clear_all     # 各テストの前にキューを空にする
```

- 「ジョブが投入されたこと（引数含む）」と「ジョブ単体の振る舞い」を別々にテストする。
- 実際に実行したいときは `Sidekiq::Testing.inline!` や `drain` を使う。

## 4. 設計上の論点（レビュー視点）

- `perform_async` を1件ずつ呼ぶと、大量件数ではRedisへの往復が増える。まとめて積む `Sidekiq::Client.push_bulk` という選択肢がある。
- ジョブ投入の**後**に管理テーブルの行を作る順序だと、ジョブが極端に早く終わった場合に行が存在しない、という競合が理論上ありうる。
- ジョブ内で対象レコードが取得できない（削除済み）場合の扱いが、設計として明示されているかを確認する。

## 5. 次の職場で最初に確認すること

1. Sidekiq直接か、Active Jobか（Rails 8の標準は Solid Queue なので、DB基盤のジョブキューの可能性もある）
2. Sidekiqは OSS / Pro / Enterprise のどれか（Batch、ユニークジョブなどの有償機能の有無）
3. リトライ方針とデッドキューの運用ルール
4. DBトランザクション中のジョブ投入ルール（`after_commit` で投入しないと、コミット前にジョブが実行されて対象が見つからない問題が起きる）
5. 並列数とDB接続プールの関係、キューの分け方

## 6. 手を動かす確認（10分）

- 自分が関わったワーカーを1つ選び、「これを2回実行されたら何が起きるか」を考える（冪等性の確認）。
- 並列数の設定と `database.yml` の `pool` を見比べる。
- `perform_async` の呼び出し箇所を検索し、トランザクションの中で呼ばれていないかを確認する。
